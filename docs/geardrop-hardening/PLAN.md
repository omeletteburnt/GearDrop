## Phase 3 — Session & auth hardening — [x] DONE (2026-09-16)

- [x] **3.1 Added `@supabase/supabase-js` (v2.116.0), migrated `src/supabase.ts`.** Replaced hand-rolled `fetch` + raw `localStorage` session juggling with `createClient()` and its built-in `auth.getSession()`/`onAuthStateChange` (auto refresh, auto persistence). Added `getSession()` (now async) and a new `onSessionChange()` subscription helper. `src/main.tsx` updated: session state now loads via `useEffect` + `getSession()`/`onSessionChange()` instead of a synchronous `localStorage` read at mount; `signOut()`, `saveListing()`, `deleteListing()`, `isAdmin()` no longer take a `session` param since the client tracks it internally. **Residual localStorage risk**: supabase-js still persists the session to `localStorage` by default (same XSS-stealable surface as before, just no longer hand-rolled) — an httpOnly-cookie session (requiring a server, which this SPA doesn't have) is a real fix but out of scope without adding a backend; noted as a NOT-handled residual risk below.
- [x] **3.2 Stopped surfacing raw Supabase error messages.** Added `friendlyAuthError()` mapping known patterns (invalid credentials, already-registered, weak password) to generic copy; unrecognized errors fall back to a single generic message. Also fixed the related silent-no-op-delete gap (PLAN item 2.4) while rewriting `deleteListing()`: it now uses `{ count: "exact" }` and throws a real "you don't have permission" error when `count === 0`, instead of the old code treating any 204 as success.
- [x] **3.3 Reviewed synthesized-email sign-up.** `identity()` normalization (`toLowerCase` + strip to `[a-z0-9_]`) plus `profiles.username unique` means two usernames that normalize to the same string (e.g. "Player_1" vs "player-1" after stripping) would collide at the **auth** layer first (Supabase would reject the second signup as "already registered" before the profile insert is even attempted), which now surfaces as the friendly "That username is already taken." message — behaviorally acceptable, no code change needed beyond the error-message mapping already done in 3.2. **Password reset is confirmed not possible** under this scheme (no real email is ever collected) — documented here rather than built, since adding a real recovery-email flow is a product decision, not a bug fix; flagged as NOT handled below.

**Verification performed:** `pnpm build` (`tsc --noEmit && vite build`) — clean, 64 modules. Live functional smoke test against production Supabase with a disposable account (`rlstest_temp_c@nyx.local`): sign-up → session returned; profile upsert → success; listing insert → success; `is_admin()` RPC as authenticated non-admin → `false`, no error; sign-out then delete attempt on the listing → `count: 0`, which the wrapper now correctly turns into a thrown permission error; sign back in and delete same listing → `count: 1`, succeeds; sign-in with wrong password → raw provider message `"Invalid login credentials"` confirmed mapped by `friendlyAuthError()` to `"Incorrect username or password."`. All behaviors matched design. **Leftover test data**: `rlstest_temp_c@nyx.local` account still exists (test listing was cleaned up as part of the test) — added to the batch of test accounts needing manual deletion.

**Self-review (OWASP-frame):** Addresses API2:2023 (session/credential handling) by moving off hand-rolled token juggling to a maintained library with real refresh handling, and API3:2023-style excessive data exposure by no longer echoing raw backend errors. **Explicitly NOT handled**: (1) localStorage remains the session store — full mitigation needs a server/httpOnly-cookie architecture this SPA doesn't have; (2) no password-reset flow exists or is proposed, since the synthesized-email scheme has no real email to reset via — this is a product-level gap, not something patched here; (3) token refresh is now handled by supabase-js automatically, but was not separately load-tested for edge cases like multi-tab session sync.
